## Integrating Email Verification Protocol

To implement an instant, cryptographic email verification flow on your website, you can integrate the experimental **Email Verification Protocol (EVP)**.

### Configure form fields

To request an Email Verification Token (EVT), you need to configure your registration or sign-in form with specific HTML attributes that the browser's autofill manager recognizes:

- **Email input field**: Set `type="email"` and `autocomplete="email"`. Use a standard light DOM `<input>` element so the browser's autofill manager can detect it.
- **Hidden token field**: Set `type="hidden"`, `autocomplete="email-verification-token"`, and specify a session-bound `nonce` attribute containing a cryptographically secure value generated by your server.

Here is a basic HTML form structure:

```html
<form id="registration-form">
  <input type="email" autocomplete="email" required />
  <input
    type="hidden"
    autocomplete="email-verification-token"
    nonce="SERVER_GENERATED_NONCE"
  />
  <button type="submit">Register</button>
</form>
```

---

### Environment configuration

EVP behavior and configuration requirements differ across local development, staging, and production environments:

#### Local development

- **Browser flags**: Enable Chrome flags:
  - `chrome://flags/#email-verification-protocol` (to turn on the protocol feature).
  - `chrome://flags/#allow-insecure-localhost` (to allow background network requests to local HTTPS endpoints).
- **TLS trust**: Direct navigate to both `https://rp.localhost` and `https://idp.localhost` and proceed past the privacy warning to trust the self-signed certificates session-wide.
- **DNS TXT delegation bypass**: Real DNS TXT delegation lookups are bypassed for local domains (e.g. `*.localhost`, `localhost`, `127.0.0.1`) in our server-side validation middleware.

#### Staging & production

- **Origin trial enrollment**: Sign up your Relying Party origin for the **Email Verification Protocol** Origin Trial via Chrome's Origin Trials console.
- **Origin-Trial header / meta tag**: Supply the origin trial token on the page serving the email form. Our server automatically injects this via the `Origin-Trial` HTTP response header. Configure this in `staging.config.json` or `prod.config.json`:
  ```json
  "origin_trials": [
    "YOUR_BASE64_ORIGIN_TRIAL_TOKEN"
  ]
  ```
- **DNS delegation record**: Configure a public `TXT` record on your email domain to delegate verification authority to your identity provider's issuer origin:
  - **Record Name**: `_email-verification.<email-domain>`
  - **Record Type**: `TXT`
  - **Value**: `iss=<issuer-origin>` (e.g., `iss=https://accounts.google.com` or `iss=https://identity-provider.example.com`)

### Issuer discovery & well-known endpoint

The email provider (Issuer) must expose its configuration metadata at a public well-known URL:
`https://<issuer-domain>/.well-known/email-verification`

- **CORS requirement**: This endpoint must serve standard CORS headers (`Access-Control-Allow-Origin: *` or matching the RP origin) to allow browser background fetches.
- **Response format**: The endpoint must return a JSON metadata object:
  ```json
  {
    "issuance_endpoint": "https://<issuer-domain>/evp-idp/issuance",
    "jwks_uri": "https://<issuer-domain>/evp-idp/jwks",
    "signing_alg_values_supported": ["EdDSA"]
  }
  ```

---

### Server-side token verification

When the form is submitted, the value of the hidden `email-verification-token` input (an SD-JWT and Key Binding JWT package separated by a `~`) must be validated on your server using these six sequential steps:

1. **Token decomposition & parsing**: Split the token into its constituent Verifiable Credential (SD-JWT) and Key Binding JWT (KB-JWT) components, then decode the headers and payloads.
2. **Local claims & session verification**: Check the basic claims without doing network or cryptographic operations (verify `email_verified` is true, the email matches the submitted email, the audience matches your origin, and the nonce matches your session-bound challenge).
3. **DNS delegation authority check**: Confirm via DNS TXT query that the email domain delegates authority to the token's `iss` issuer (direct domain matching is bypassed locally).
4. **Issuer discovery & JWKS fetching**: Fetch the well-known configuration and JWKS public keys from the issuer's authoritative origin.
5. **Issuer signature verification**: Validate the signature on the SD-JWT credential using the fetched issuer public keys.
6. **Key binding verification**: Extract the browser's ephemeral public key from the validated SD-JWT and verify the signature on the KB-JWT to prove ownership of the private key.

### Origin Trial Notes

Starting with Chrome 150, Relying Parties must sign up for the EVP origin trial to test the feature on live domains. Key considerations include:

- Only the Relying Party (verifier) needs the origin trial token; Identity Providers (like Gmail, which is participating) do not need to register.
- The trial is intended to gather feedback on verifying emails seamlessly without sending OTPs or magic links, thus reducing friction and latency.
- Due to traffic limits on origin trials, always deploy EVP as a progressive enhancement, falling back to traditional OTP or magic links if the token (`email-verification-token`) is missing.
